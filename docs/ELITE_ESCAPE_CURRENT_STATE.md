# Elite Escape — Current State (as of this audit)

This is a factual inventory of what actually exists and runs today, across
both repositories. Nothing in this document is aspirational — if it's listed
here, it is built, was tested (curl and/or Playwright end-to-end), and is on
`main`.

## Two separate codebases

| Repo | Purpose | Stack |
|---|---|---|
| `elite-escape-tourism` | Public marketing website | Static HTML/CSS/JS, no backend |
| `eliteescape2` | Internal business platform | Node/Express API + SQLite + vanilla-JS admin dashboard |

They are connected by exactly one integration point: the website's forms and
chat widget POST to the platform's public API
(`POST /api/public/leads`, `POST /api/public/ai/chat`), which is CORS-locked
to the website's origin and rate-limited. No shared database, no shared
session, no shared codebase.

## `elite-escape-tourism` (public website)

- **691 static HTML pages**, generated by a custom Node build script
  (`scripts/build.mjs`) — destinations, holiday packages, visa pages (49
  countries), UAE attractions (14), blog posts, guides.
- Self-hosted variable-width fonts (Fraunces + Figtree, WOFF2) — no Google
  Fonts dependency.
- All imagery is self-hosted, WebP, converted from real downloaded photos
  (no third-party hotlinking — Unsplash/Pexels/Pixabay were all tried and
  are blocked by this environment's egress policy, which also means none of
  those are usable at runtime in production either without a paid API and a
  different hosting environment).
- Client-side chat widget and lead-capture forms (`assets/js/main.js`) that
  currently do **static, regex-based reply matching** — not connected to
  the platform's real AI agents yet. They do POST captured leads to the
  platform's `/api/public/leads`.
- `sitemap.xml`, `robots.txt`, `manifest.webmanifest` exist.
- No CMS, no database, no server-side rendering, no build-time data from the
  platform. Content changes require editing the build script/templates and
  regenerating.

## `eliteescape2` (internal platform)

**Stack:** Express 5, Node's built-in `node:sqlite` (no external DB driver),
`bcryptjs`, `zod`, `cookie-parser`. No framework beyond Express. Frontend is
hand-written HTML/CSS/vanilla JS (`web/`), served as static files by the
same Express process. No React, no build step, no bundler.

**Auth & access control**
- Session-cookie auth (`ee_session`, 7-day expiry), bcrypt password hashing.
- Role-based permissions via a `role_permissions` join table, enforced in
  Express middleware (`auth(["perm.code"])` per route).
- Roles: owner, admin, sales, ops, finance, hr, marketing. Owner/admin hold
  every permission; other roles hold their module's permissions only.
- Self-registration (`POST /api/auth/register`) creates only the first
  (bootstrap) account as owner, then permanently locks itself — every
  account after that is admin-created via `POST /api/admin/users`. Login is
  rate-limited (10/10min/IP). Self-service password change exists.
- **No MFA. No field-level or record-level access restriction — permissions
  are module-level only** (e.g. `crm.read` sees every lead, not just "my
  leads"). No session-device fingerprinting beyond the cookie itself.

**CRM**
- `customers`, `leads` (with `interest_type`, `status` pipeline: new →
  contacted → quoted → won/lost), `lead_activities` (timeline notes).
- No opportunities as a distinct stage before "lead," no quotation
  versioning, no formal sales pipeline stages beyond the 5 listed.

**Travel operations**
- `bookings` + `booking_items` — a single generic booking record with
  free-text line items (description/qty/unit price). **Not** separated into
  dedicated Holiday/Flight/Hotel/Transfer/Attraction/Insurance service
  tables with their own fields (supplier, dates, confirmation numbers).
- No traveler records (name/passport/DOB) distinct from the customer. No
  supplier-facing data at all — no supplier table, no purchase orders tied
  to a specific service, no supplier confirmation tracking.
- No visa case management — visa is just one `interest_type` value on a
  lead/booking, with no case, applicant, document, or status-history model.

**Accounting**
- `invoices`, `invoice_items`, `payments`. Sequential invoice numbering
  (`INV-2026-0001`, gap-free, UAE-FTA-style) via an atomic counter table.
  5% UAE VAT computed and stored (`vat_rate_bps`, `vat_amount_aed`).
- **This is single-entry invoice/payment tracking, not double-entry
  accounting.** There is no chart of accounts, no general ledger, no
  journal entries, no balance sheet/P&L, no bank reconciliation, no
  multicurrency, no cost centers. Money fields are stored as `REAL`
  (floating point), not fixed-point decimal.
- No UAE eInvoicing (FTA ASP) integration of any kind — invoices are
  internal records only, not submitted anywhere.
- No supplier bills, no payables, no refunds/credit notes/debit notes as
  distinct entities.

**HRMS / Payroll / Procurement**
- `employees`, `leave_requests` (approve/reject; approval auto-sets
  employee to `on_leave`).
- `payroll_runs` + `payslips` — monthly runs, auto-generated from basic
  salary, editable allowances/deductions while in draft, locked once
  processed, `draft → processed → paid` lifecycle. No attendance tracking,
  no shifts, no end-of-service calculation, no employee document
  storage/expiry tracking (passport/Emirates ID/visa).
- `vendors` + `purchase_orders` (sequential `PO-2026-0001` numbering,
  approval workflow). This is the closest thing to "supplier management"
  that exists, and it's generic (not travel-specific — no supplier rates,
  no per-service supplier bookings).

**AI**
- Two agents (Receptionist, Travel Consultant) via a `mock`/`anthropic`
  provider switch. Mock mode does real regex intent-matching and calls real
  tools against the real database (`create_lead`, `get_customer_summary`,
  `request_human_handoff`) — genuinely functional today with zero external
  dependency. The `anthropic` code path (Messages API, tool-use loop) is
  fully implemented but has never run against a real API key (none
  available in this environment).
- Conversations/messages persist; staff can view threads in the admin UI.
- **This is not the 8-agent AI workforce the new spec describes** — no
  Visa Assistant, Sales Assistant, Operations Assistant, Finance Assistant,
  Marketing Assistant, or Executive Assistant exist. No AI usage/cost
  tracking, no per-agent evaluation dataset, no approval-gate for
  high-risk AI actions (the two existing tools are all low-risk: create a
  lead, read a summary, flag for a human).

**Marketing**
- `campaigns` (email/WhatsApp) targeted at customers or leads by
  interest/status/source, with a live audience preview and send history.
  Sends go through a `console` provider (logs to stdout) — **no real email
  or WhatsApp sending integration exists.**
- A dependency-free SEO auditor (regex-based title/meta/H1/alt-text/word-
  count checks) that crawls real pages and a content-calendar CRUD. No AEO/
  AIO/GEO tooling, no Search Console integration, no social media
  scheduling/publishing, no ad-platform integration, no attribution beyond
  the audit/campaign tables themselves.
- **Elite Reach does not exist in any form** — no signal ingestion, no
  connectors, no intent graph, no scoring, no demand radar. It is a wholly
  new system per the new spec, not an existing one to migrate.

**Platform administration**
- User management (create, role change, activate/deactivate, force-logout
  by revoking sessions), a full audit-log viewer, and a system-health
  dashboard (business KPIs + in-memory request/error counters).
- Single-tenant: one organization, no branches/departments/legal-entity
  model, no per-org settings (currency/language/tax/brand).

**Portals**
- There is exactly one UI: the internal admin dashboard (`web/index.html`),
  used by staff. **No customer portal, no supplier portal, no employee
  self-service portal.** Customers and suppliers have no login of any kind.

**Mobile**
- None. No React Native project, no Expo scaffold. This sandbox has no
  Xcode/Android Studio/emulator, so this was explicitly deferred by the
  user's own decision earlier in this project rather than built blind.

**Infrastructure**
- Single Node process, SQLite file on local disk, no Docker, no CI/CD, no
  staging/production environment separation, no queue (no Redis/BullMQ —
  the two things that resemble "background jobs" are the in-memory rate
  limiter and console-log notification provider), no object storage (file
  uploads are not implemented at all — no document management module
  exists), no backups, no monitoring beyond the in-process metrics endpoint
  built in Phase 8, no automated test suite (`npm test` script exists in
  `package.json` but no test files have been written).

## Bottom line

What exists is a real, working, single-tenant internal tool covering CRM,
generic bookings/invoicing, HR/payroll, procurement, two working AI agents,
marketing campaigns, an SEO auditor, and platform administration — verified
end-to-end at every step. It is built on a deliberately minimal stack
(Express + SQLite + vanilla JS, zero build tooling) that was the right size
for an 8-phase incremental build in this environment.

It is **not** the enterprise, multi-module, multi-portal, mobile-inclusive,
Next.js/NestJS/PostgreSQL/Redis/pgvector/S3/React-Native platform described
in the new master spec. See `ELITE_ESCAPE_GAP_ANALYSIS.md` for the itemized
gap and `ELITE_ESCAPE_ARCHITECTURE.md` for the stack-decision this implies.
